# 两地开发合并指南（Git 操作手册）

> 本文写给：**在旧版本基础上做了大量本地开发、但还没有上传的一方**（下称"协作者"）。
> 目的：让协作者把手头的代码安全地合并到仓库最新版本上，**双方任何代码都不丢失**。

---

## 一、开始之前，先看这 3 句话

1. **`git pull` 不会覆盖你没保存的修改。** git 发现拉取会动到你正在编辑的文件时，会直接拒绝并报错，不会静默覆盖你的代码。
2. **绝对不要执行**这三个命令（会丢掉你所有本地修改）：
   - `git reset --hard`
   - `git checkout .`
   - `git clean -fd`
3. **动手前先备份**：把整个项目文件夹复制一份到别处（比如桌面）。就算操作失误也有后悔药。

---

## 二、正式合并前，双方都先做备份（重要）

### 仓库主人侧（已有 GitHub 远程）

1. **云端快照（推荐）**：给当前状态打一个标签并推送到 GitHub，之后随时可以一键回退到合并前的样子：
   ```bash
   git tag backup-pre-merge-20260818
   git push origin backup-pre-merge-20260818
   ```
   （此标签已由主人打好并推送，协作者无需操作。）
2. **本地备份分支**（可选，更保险）：
   ```bash
   git branch backup-pre-merge
   ```

### 协作者侧（代码从未上传，备份最重要）

**双保险，两个都做：**

1. **整文件夹备份（5 秒，最直观）**：把整个项目文件夹复制一份/压缩成 zip，命名如 `项目名-合并前备份-日期`，放到桌面或网盘。

2. **git 层备份（推荐，可远程）**：把本地代码提交并推送到 GitHub 上自己的分支，这样即使电脑出问题也有云端副本：
   ```bash
   git add -A
   git commit -m "wip: 我的本地开发（合并前备份）"
   git branch my-work                 # 本地分支标签
   git push origin my-work            # 推送到 GitHub（云端备份）
   ```
   > 如果提示 `remote origin not found`，先执行：
   > `git remote add origin https://github.com/RichardChen003/ai-teacher-platform.git`

## 三、先确认你的项目属于哪种情况

打开你的项目文件夹，看看里面有没有一个叫 **`.git`** 的隐藏文件夹：

| 情况 | 判断 | 走哪条路 |
|------|------|----------|
| 情况一 | 有 `.git` 文件夹（你当初是用 `git clone` 或 git 方式下载的） | 走【第三部分】 |
| 情况二 | 没有 `.git` 文件夹（你是下载 ZIP 解压后开发的） | 走【第四部分】 |

---

## 三、情况一：有 `.git` 文件夹（git 方式下载的）

按顺序做以下 5 步。**每步都写了命令的作用和成功标志，照做即可。**

### 第 1 步：备份（必做，5 秒）

把整个项目文件夹复制一份，例如重命名为 `项目名-备份-日期`，放到桌面。

### 第 2 步：打开命令行终端

在 Windows 上：进入你的项目文件夹 → 在文件夹空白处**右键** → 选择 **"Git Bash Here"**（或"在终端中打开"）。
之后的命令都在这黑窗口里输入，每次输完按回车。

### 第 3 步：把你现在的代码保存为"自己的分支"

依次输入下面两条命令：

```bash
git add -A
```
> 作用：把**你所有修改过的文件**加入待保存列表。

```bash
git commit -m "wip: 我的本地开发（合并前快照）"
```
> 作用：把你当前的代码保存成一个快照。
> ✅ 成功标志：显示类似 `[main xxx] wip: 我的本地开发` 的一行文字。

```bash
git branch my-work
```
> 作用：给你的代码再贴一个**永久标签**（名为 my-work）。
> ✅ 成功标志：不报错即成功。从此你的全部工作都安全保存在 `my-work` 里，后面怎么折腾都不会丢。

### 第 4 步：下载最新代码并"搬"上去

```bash
git fetch origin
```
> 作用：把仓库主人的最新代码下载到本地（**不会动你的文件**，只是下载）。
> ✅ 成功标志：显示类似 `From github.com:...` 的一堆文字，没有红色报错。
> ⚠️ 如果提示 `remote origin not found`：先执行 `git remote add origin https://github.com/RichardChen003/ai-teacher-platform.git`，再重试这条。

```bash
git rebase origin/main
```
> 作用：**把你第 3 步保存的修改，从旧代码上"搬"到最新代码上**（类似把贴纸从旧底板揭下来贴到新底板）。
> ✅ 成功标志：没有任何提示，直接回到命令提示符。
> ⚠️ 如果提示 `CONFLICT`（冲突）：**别慌，代码没丢**，跳到【第五部分】照着处理。

### 第 5 步：把合并结果传回 GitHub

```bash
git push origin HEAD:main
```
> 作用：把你合并好的代码推送到 GitHub 的 main 分支。
> ✅ 成功标志：显示 `main -> main` 之类的内容，没有报错。

**到这里就完成了。** 仓库主人 `git pull` 一下就能看到两边合并后的完整代码。

---

## 四、情况二：没有 `.git` 文件夹（ZIP 下载开发的）

你没有 git 历史，需要先"补上 git"，再走上面流程：

```bash
# 在项目文件夹打开终端后，依次输入：
git init
git add -A
git commit -m "初始提交：我的本地开发"
git remote add origin https://github.com/RichardChen003/ai-teacher-platform.git
git fetch origin
git rebase origin/main
```

前 3 条是"初始化 git 并保存你的代码"，后 3 条与【第三部分】第 4 步相同。
合并完推回：`git push origin HEAD:main`

## 五、遇到冲突怎么办（手把手版）

"冲突" = 你和主人**改了同一个文件的同一个地方**，git 不知道该听谁的，于是让你来选。**代码不会丢，只是需要你决定。**

### 第 1 步：看哪些文件冲突了

```bash
git status
```
输出里会看到类似 `both modified: apps/web/src/pages/xxx.tsx` 的文件，这些就是冲突文件。

### 第 2 步：打开冲突文件，找标记

用编辑器（VS Code 等）打开冲突文件，搜索这些标记：

```
<<<<<<< HEAD
（这里是我的/主人的最新代码）
=======
（这里是你写的代码）
>>>>>>> my-work
```

- **`<<<<<<< HEAD` 到 `=======`** 之间 = 主人的版本
- **`=======` 到 `>>>>>>>`** 之间 = 你的版本

### 第 3 步：每个冲突块做选择

- 要主人的：删掉 `=======` 到 `>>>>>>>` 之间的内容，以及三行标记
- 要你的：删掉 `<<<<<<< HEAD` 到 `=======` 之间的内容，以及三行标记
- 两边都要：把两段都保留，删掉三行标记

改完保存文件。

### 第 4 步：告诉 git "这个文件处理完了"

```bash
git add 冲突文件名
```

### 第 5 步：全部处理完后继续

```bash
git rebase --continue
```
> 重复第 1~5 步直到不再提示冲突，然后回到【第三部分】第 5 步推送。

### 冲突文件的取舍建议（重要）

| 文件类型 | 建议 |
|----------|------|
| `infra/d1/*.sql`（题库、知识点数据） | **直接用主人的版本**（主人重做了整套 3403 题题库）；如果你也有自编新题，单独发给主人合并 |
| `scripts/gen-*.py`、`scripts/gen-*.mjs`（出题生成器） | 直接用主人的版本（已大规模重写） |
| `apps/web/src/pages/*`（页面） | 逐个看：主人加的功能保留，你的定制也保留，两边都留 |
| `apps/api/src/*`（后端逻辑） | 逐个看：主人的修复保留，你的扩展保留 |

## 六、如果上面操作还是搞不定：3 个替代办法

### 方案 A：只把分支推上来，让主人帮你合并（最省事，推荐）

```bash
git add -A
git commit -m "wip: 我的本地开发"
git branch my-work
git push origin my-work
```
> 作用：把你的代码作为一个叫 `my-work` 的分支推上 GitHub。
> 之后**什么都不用做**，主人会在他那头处理合并和冲突，合并好后通知你 `git pull` 即可。

### 方案 B：导出一个补丁文件发给主人

```bash
git diff <你最初下载时的版本号> -- 你改过的文件 > my-changes.patch
```
> 如果不知道版本号，就用：`git log --oneline | tail -1` 看最早的提交号。
> 把生成的 `my-changes.patch` 文件发给主人，主人帮你应用并核对。

### 方案 C：列文件清单，逐个确认

在项目文件夹终端执行：

```bash
git status
```
把列出的文件清单发给主人，两边对照着逐文件确认合并方式（可以用 Beyond Compare 或 VS Code 对比工具）。

---

## 七、以后怎么避免再出现这种情况

1. **先拉再改**：每天开工前先 `git pull`，改完一小块就提交推送，别攒一大堆。
2. **开自己的分支**：在 GitHub 建一个如 `dev-你的名字` 的分支，定期推送，主人 review 后合入 main。
3. **小步提交**：一次改动别太大，提交说明写清楚，以后冲突也好解决。

---

> 任何一步卡住了：把终端里红字报错截图发给主人即可，主人能帮你判断下一步。
